# FEATURE.md — `detail` (the Detail primitive, `lib/detail`)

**Status:** `active`
**Tier:** `2`
**Last updated:** `2026-09-17`

---

## Purpose

ONE core component per record type — header, source health strip, fields, associations,
history — wrapped once so it shows as a **window** (default), a **docked** side panel, or a
**page**, chosen by the person's `ui.detail.default_presentation` setting. Every surface that
names a record opens it through the one opener; agents' item cards, list rows and doors all
land here. Package-shaped: see [README.md](./README.md) for the boundary and the extraction plan.

## Entry points

**Routes**
- `app/(core)/detail/[type]/[id]/page.tsx` — the page presentation (`?l=type.id,…&i=<n>` = list context).
- `app/(core)/detail/page.tsx` — THE feature-visibility surface: one real file of yours in all three presentations, with each deep link and the same record at 390px. It is in `(core)` because `(dev)` is compiled out of the `core` profile the preview server and the main site run, so the old demos-only path answered with a 307 nobody could follow (D6, 2026-09-17).
- `app/(dev)/demos/detail-primitive/page.dev.tsx` — the same surface for the demos deployment. Body for both: `features/window-panels/detail/DetailShowcase.tsx`.

**Hooks**
- `useOpenDetail(warmType?)` (`useOpenDetail.ts`) — THE opener. Resolves the setting, opens in place; `page` navigates.
- `useDetailCore(data, presentation, { onClose? })` (`core/useDetailCore.ts`) — the core as state. `onClose` is for the in-place presentations; the page needs none and is left through `core.leave` (D1).
- `useDetailKeyboard` — Escape · `[` / `]` always · ArrowUp/Down/Left/Right when the body is not the scroll target · Cmd/Ctrl+Enter.
- `useDetailHost` / `DetailHostProvider` (`host.tsx`) — the ports.
- `savePresentation` (`features/window-panels/detail/savePresentation.ts`) — THE write port bound by `DetailHost`; a per-type save (and its removal) goes through `setUserKnobMapEntry` (`lib/scoped-config/service.ts`).
- `trimListContext` (`listContext.ts`) — the list context capped before it rides a URL (NEW-7).

**Components**
- `DetailWindowPresentation` · `DetailDockedPresentation` · `DetailPagePresentation` (`presentations.tsx`).
- `DetailTitle` · `DetailActions` · `DetailRecordMeta` (`core/DetailHeader.tsx`) · `DetailBody` (`core/DetailBody.tsx`) · `DetailPresentationPane` (`core/DetailPresentationPane.tsx`).

**The one singleton opener**
- `openDetailSingleton` (`features/window-panels/detail/openDetailSingleton.ts`) — the ONLY place `detailWindow` / `detailDocked` are opened. Both opener hooks and the `?panels=` hydrator go through it, which is what makes the replacement announcement impossible to forget (D8).

**Overlays (host)**
- `detailWindow` (window, `mobilePresentation: "drawer"`, `urlSync.key: "detail"`) → `features/window-panels/windows/detail/DetailWindow.tsx`.
- `detailDocked` (sheet, `urlSync.key: "detail"`) → `features/window-panels/windows/detail/DetailDocked.tsx`.
- Openers: `features/overlays/openers/detailWindow.tsx`, `detailDocked.tsx`.

**Redux slice(s)**
- None new. The overlay slice carries the instance (`type`, `id`, `seedName`, `seedAbout`, `listItems`, `listIndex`); the window manager slice sees the window through `WindowPanel` as usual. Decision recorded 2026-09-17: every piece of detail state is either the record (loaded per mount) or the open request (already in the overlay slice), so a third slice would be a parallel store.

Were it ever missing, `knob_resolve` raises for the key by design, `DetailHost` catches that, warns once per tab naming the file, and the default answers.
- `platform.feature_knob` row `ui.detail` / `list_context_max_ids` — how many records of the opening list may ride a URL, page presentation AND detail-window deep link (integer, live default 200 → 100 once the pending file below is applied, **organization**-overridable). `migrations/detail_list_context_max_knob.sql`, **APPLIED and ledgered 2026-09-17 20:04Z** (the chair applied it through the sanctioned path). Were the row ever absent, `knob_resolve` raises for the key, `getSessionKnob` logs it and answers `undefined`, and `detailListContextMax` uses the module default of 200 — the cap is never absent, only unconfigurable. 🚨 **The record count is not the budget: BYTES are, and they belong to the FINAL URL** (NEW-12, then NEW-19 / NEW-20). `migrations/detail_list_context_max_ceiling.sql` is **APPLIED and ledgered 2026-09-17 20:48:24Z** by the chair through the sanctioned path (checksum `5d7346eb…`; read live from `platform.feature_knob` and `public._schema_migrations` on 2026-09-17 by F-31 — an earlier line here called it "pending", which was NEW-21). It left the live row at `max_value = 500`, `default_value = 200` and a basis sentence claiming 200 uuid records travel. **They never did**: the budget was measured on the list VALUE before `URLSearchParams` re-escaped it, so a uuid list stopped at 139 and every value from 139 to 500 behaved identically. The client now measures the FINAL serialized URL against `DETAIL_URL_BUDGET_BYTES` (8000 — the request line) with the rest of the address RESERVED, and `detailListContextMax` clamps to `DETAIL_LIST_CONTEXT_MAX_IDS_CEILING` (100, the count that travels in every presentation). 🚨 **`migrations/detail_list_context_max_deliverable.sql` is PENDING** (F-31, 2026-09-17): it lowers the row's `max_value` and starting value to the same 100 and rewrites the basis with the measured per-record cost in each spelling, so the settings screen cannot offer records the URL can never carry. Until the chair applies it, the screen offers up to 500 and the client quietly lowers it — a stale offer, never a breakable link.
- `public.version_list(p_token, p_id)` — the history section (`history.row_versions`, viewer-gated).
- The record itself — whatever the registration's `load` reads (item-presentation: the registry's `detailSource`, RLS).

**Key types** (`types.ts`): `DetailPresentation`, `DetailRecordType`, `DetailField`, `DetailSourceHealth`, `DetailListContext`, `DetailInstanceData`, `DetailHistoryEntry`.

## Key flows

1. **A card is clicked.** `useOpenItemPresentation` → `useOpenDetail()({ type, id, seed })` → `host.resolvePresentation` (cached knob; RAISES when unregistered → toast + window) → `host.open({ presentation, data })` → opener dispatches `openOverlay("detailWindow" | "detailDocked")`, or `router.push("/detail/<type>/<id>")` for `page`.
2. **The overlay renders.** `OverlayController` block → lazy `DetailWindow` → `<DetailHostProvider ports={{ resolveType, shells: { Window } }}>` → `DetailWindowPresentation` → `useDetailCore`: `resolveType(type)` (item-presentation registry) → `useDetailRecord` (abortable load) → title/fields/health → shell slots filled → `DetailBody` sections.
3. **Switch presentation from inside, or leave the page.** `DetailActions` → `core.switchTo("docked")` → `host.open(docked)` then `host.close(window)`. Leaving the page — the Back chevron, Escape, or a switch — is ONE exit, `core.leave`: `host.navigate.canGoBack(ref)` decides, `back()` only when THIS tab pushed the page itself, otherwise `toRecordHome` replaces it with the record's own route (or `/dashboard`). Never a bare `back()`, and never an exit passed in by a route (D1 twice).
4. **Deep link.** `?panels=detail:task.<id>:as-docked` → `UrlPanelManager` → hydrator `detail` → `openDetailSingleton` → `openOverlay("detailDocked")`; the mounted shell re-registers the same token (`useUrlSync` / `WindowPanel` urlSync props) so the URL round-trips. A link naming two records announces the one it closed, like every other opener (D8).
5. **`[` / `]`, and the arrows.** `useDetailKeyboard` on the presentation root → `core.list.next()` → `host.open` with `list.index + 1` (singleton retargets) or `toPage(next, { list })`. The arrows do this only when the body is not scrollable; when it is, they scroll it (NEW-5).
6. **The setting is changed — or taken back — from the record.** `DetailPresentationPane` at the foot of every detail → `host.savePresentation({ presentation, forType })` → `platform.knob_override_set` at the person's rung. `forType` changes ONE entry of the per-type map through `setUserKnobMapEntry`: the door replaces the whole json value, so the write re-reads the ladder first (past the 60s cache) and **REFUSES, with the sentence the pane renders, when the current map cannot be read** — a failed read merged into `{}` wrote a one-entry map over every other type the person had set (Bugbot, frontend PR 228). "Use the default for <type> records" removes that entry through the same primitive with the key absent, clearing the whole override row when it was the last one (NEW-2); when the exception is the ORGANIZATION's, the pane says so and claims no save. 🚨 **After a successful removal the pane RE-READS the ladder** (`host.reReadPresentation`, which invalidates the 60s cache first) and names the rung that answers now — the person's own way, or the organization's exception that survived their removal, or plainly that it could not be read. It used to promise "<Type> records now open the way you normally open records" while the organization's entry still won on the next open (NEW-10). It registers `core.keyboard.registerSave` while open, so Cmd/Ctrl+Enter saves it — the chord's only caller until a record type ships an editable body.

## Invariants & gotchas

- **THE type map is `features/item-presentation/registry.tsx`** (chair ruling 2026-09-17) — `resolveItemDetailType` adapts it; never a second registry. Unknown types still resolve (neutral fallback, seed-only), exactly as the old window did.
- **`resolveType` and the shells are bound by each presentation's entry, not at boot.** The window shell parses `WindowPanel` and the type map pulls the right-click menu; `DetailHost` (boot, in `app/Providers.tsx`) binds only what `useOpenDetail` needs. `useDetailHost` throws naming a missing port; `requireShell` / `requireResolveType` name the entry that forgot.
- **The registry `urlSync.key` wins over shell props** (`resolveWindowUrlSyncKey`); the shell supplies only the instance (`type.id`) and `as`.
- **`docked` is not `drawer`.** `drawer` in this codebase is the vaul bottom sheet (`mobilePresentation: "drawer"`); the third presentation is `docked` (chair ruling 2026-09-17).
- **Escape is handled on the presentation root (capture)**, and `MatrxDynamicPanelHost` also closes on document Escape — both dispatch the same idempotent close.
- **Keys read on the root ignore typing targets** except Cmd/Ctrl+Enter, which is the point of a field.
- **A `<token>_id` column becomes a door only when its value is a real uuid AND the token has a door** (`tokenFromColumnName` is strict) — a wrong link is worse than no link.
- **The associations section shows only for tokens in `ASSOCIATION_TARGET_TYPES`**; default tokens `task, note, file, project` minus the record's own token.
- **Only `ready` is a loaded row, and a load that is not one invents NOTHING.** The title comes from the loaded row or the seed; with neither it says what is happening, sets `data-detail-title-standin`, and drops the record's doors. `status: "none"` — a type with no `detailSource` — is the ABSENT state, not a successful load (D5 + NEW-1: treating it as loaded put `Untitled File` over "no details available"). 🚨 **But the absent state is never a SENTENCE and never a file path** (NEW-9): round 2 put "No detail is registered for session records" where the record's NAME goes and printed `features/item-presentation/registry.tsx` at the person, so a real record became a named dead end. The record is now named from what is certain — `<Type> <first 8 of the id>` — the body says in one plain sentence that nothing more about it is stored here, the DOORS STAY (`core.doorsAvailable`: a question about the record, not about its name — only a failed or missing read drops them), and the registry remedy is a `console.warn` once per type per tab, where the developer is. The census behind it: `agent`, `note`, `structured_list` and `picklist` gained the `detailSource` their own `enrich` already read; `session` is the one type deliberately left sourceless (no single canonical table) and says so in the registry. The skeleton says it is still waiting after `SLOW_LOAD_NOTICE_MS` (6s) rather than shimmering silently.
- **The header's action cluster is icons only, at every width, AND the title is laid out in the same flex row as the actions.** `sm:` answers the VIEWPORT, not the 540px window, so a `sm:`-revealed uuid in the bar always overlapped the centred title (D4). The id and the type chip live in `DetailRecordMeta` at the top of the body; the name never steps aside (D2). `WindowPanel` drew an OPEN window's title in an `absolute inset-x-0 … px-16` layer with no gap reserved for the action zone, so a long name ran under the icons whatever the detail did — it is now a `min-w-0 flex-1` flex child that truncates instead (D4/NEW-4, geometric, NO SCREEN WAS SEEN). `SidePanelSurface`'s `PanelHeader` wraps: the name and the close control hold the first line and the action cluster takes a second one when it does not fit, because under `pointer: coarse` the cluster is ~300px of a 390px phone drawer (NEW-4).
- **The docked presentation starts below the app shell header** because `SidePanelSurface` pads its fixed container with `var(--shell-header-h, 0px)` — the class fix, for every panel built on that surface (D3). `--shell-header-h` (2.75rem) is the ONE token for that height; `--header-height` (2.5rem) is the pre-shell ResponsiveLayout token, and padding with it left the panel 4px over the header's right-hand cluster. The admin tree's 2.5rem is declared ONCE, on `<body>`, because the panel is portaled into `#glass-layer` outside `.shell-root`.
- **The window and the docked panel are singletons, they say what they closed, and there is exactly ONE opener.** `openDetailSingleton` is the only place either overlay is opened — both opener hooks and the `?panels=` hydrator go through it — and it calls `announceSingletonReplacement` (`singletonReplacement.ts`), which names the replaced record with an Undo. Round 1 put the announcement in the two opener hooks, and the hydrator (a third opener nobody remembered) replaced records in silence on the very path D8 was found on (D8, twice). A literal `openOverlay({ overlayId: "detailWindow" … })` anywhere else is a second opener, and a census test fails on it.
- **Arrowing between records REPLACES the detail's one history entry.** `openNeighbour` passes `replacing: <the record showing now>` to `navigate.toPage`, and the host `router.replace`s while carrying the replaced record's "this tab pushed a detail page" answer forward. Twenty records used to mean twenty pushes, so Back walked back through every record and the chevron labelled "Back" returned to the previous RECORD rather than the list (NEW-14). Leaving is still the one guarded exit (`core.leave`), which now lands on the list or the record's home. Opening a page from another presentation still PUSHES — that is what opening a page is.
- **The header's name has a floor and the action cluster collapses first.** `DETAIL_TITLE_MIN_WIDTH_CLASS` (`min-w-[6rem]`) under the name, and below `DETAIL_HEADER_COMPACT_BELOW` (`@max-[26rem]/window-header`) the open-as icons and copy move into an overflow menu (`lib/detail/core/headerGeometry.ts`). The breakpoint is a CONTAINER query on `WindowPanel`'s header (`@container/window-header`), never a `sm:` viewport class — at the Detail window's own `minWidth={360}` the 96px traffic-light spacer plus the ~200px cluster left the name about 60px (NEW-8). Previous / next stay in the bar at every width. **GEOMETRIC — NO SCREEN WAS SEEN**; the guard asserts the structure and that the rendered classes match those constants.
- **The page route seeds from the opener when the navigation came from inside this tab** — `pageSeedHandoff.ts`, module scope, single use, 30s — so a record whose type stores nothing more here still shows the name the surface that opened it was holding. A name is never put in the URL: it is not identity and a shared link would carry one person's stale copy (NEW-9).
- **`/detail/**` is in `utils/auth/protected-routes.ts`** — a shared record link is a closed door for a guest, not a broken record (D7).
- **The list context is CAPPED before it rides a URL — by records AND by the WHOLE URL's bytes, in ONE function.** `trimListContext` (`lib/detail/listContext.ts`) obeys `ui.detail.list_context_max_ids` *and* `DETAIL_URL_BUDGET_BYTES` (8000 characters — the request line), measured on the FINAL serialized address with `reservedBytes` covering the path and any query the value is merged into (NEW-19: the old 6,000-character allowance for the list value alone let a window deep link reach 7,416 characters and a detail page carrying a window reach 13,433, past the request line, because `UrlPanelManager` re-escapes the token through `URLSearchParams`; `panelListValueBytes` and `finalPanelUrlLength` are what the guard measures). It keeps the window around the current record and sets `trimmedFrom`; `DetailRecordMeta` then says how many of how many records the arrows can reach. Both the page query (`encodeListQuery`) and the window's `?panels=` token (`detailListToUrlArgs`, which measures its own longer escaping) go through it, and both read the cap through the ONE resolver `resolvedListContextMax()` (`features/window-panels/detail/listContextCap.ts`) → `detailListContextMax`, which never returns more than the ceiling the budget can honour. A record count alone was the defect: uncapped, 500 rows was >20 KB (NEW-7); capped at 200 ids, a 30-character type token was still 13.6 KB and the knob's own live max of 2000 was 84 KB (NEW-12). `lib/detail` never reads the ladder — the host resolves it and passes the number in.
- **The trim TRAVELS THROUGH THE ARROWS TOO.** `openNeighbour` spreads the whole list context forward (NEW-19's sibling, NEW-18): it used to rebuild `{items, index}` only, so the FIRST arrow press dropped `trimmedFrom` and the next record presented the trimmed window as the whole list — in the window payload and in the page URL's `lt=` alike. The payload guard could not see it, because it tested only the round trip; `lib/detail/__tests__/the-trim-travels-through-the-arrows.test.tsx` drives the arrows.
- **The trim TRAVELS.** `trimmedFrom` is part of the overlay payload (`overlayPayloadForDetail` → `readDetailOverlayData` → `toDetailInstanceData`), so a trimmed page switched to a window or a docked panel — and the Undo re-open — still says "200 of 500" instead of presenting the window as the whole list (NEW-13). A field left out of that payload is a field the window silently does not have.
- **A detail WINDOW's deep link carries its list.** The `?panels=detail:<type>.<id>:as-window` token carries `l` / `i` / `lt` beside `as`, so a refresh keeps the previous / next controls and the counter (NEW-15). The token grammar splits on `,` `:` `_` and `-`, so the list value is escaped to hold none of them (`encodePanelArgValue`); `parseParams` also splits an arg pair on its FIRST hyphen only, because splitting on every hyphen truncated any value containing one.
- **The keyboard model is bound on EVERY SLOT the presentation fills, not only the body** (NEW-22). `titleNode` and `actions` render inside the host's shell, outside the body's root, and no shell in this app handles a keystroke — so Escape, the arrows and Cmd+Enter did nothing from the copy-id control, a presentation icon, a chevron or the overflow trigger, in all three desktop presentations (a phone hid it: the docked and window presentations are a `vaul` Drawer, which handles Escape itself). `KeyboardSlot` / `KeyboardActionsSlot` in `presentations.tsx` carry the same capture handler. 🚨 **Cmd+Enter never vanishes either**: with no save registered it says there is nothing to save on this record, rather than swallowing a deliberate keystroke.
- **A history row never drops WHO** (NEW-23). The actor used to render only when `tokenFromColumnName("actor_id")` named a token, and it names none — no `actor` / `user` token has a door — so every row threw the id `version_list` returns away. `DetailBody` asks the map for each column an author is spelled as (`actor_id`, `user_id`, `person_id`, `created_by_id`), renders the first that has a door as a chip, shows the raw value under "Changed by" when none does, and says "No person recorded for this change" when the row records nobody.
- **A record's absent state promises only the controls that RENDERED** (NEW-17). "The controls above still open it where it lives" was a fixed string, printed for `session` — a registered type with no `entityToken`, whose header shows no door — and for every unregistered type. The sentence is derived from `core.canOpenElsewhere`, which asks the host's new `doors.hasDoor(token, id)` (the same `resolveEntityDoors` answer `EntityDoorControls` renders from).
- **A `.` or a `:` in a type token or an id never retargets the record** (NEW-25). Both URL spellings — the page query's `type.id` list entries and the `?panels=detail:` instance key — split on the first dot, so `{type: "gr.ant", id: "x.y"}` came back as `{type: "gr", id: "ant.x.y"}`. `encodeRefPart` / `decodeRefPart` (`listContext.ts`) escape `.` `:` `,` on encode, in the ONE encoder both spellings share, which is what makes the split unambiguous rather than lucky. `sc-domain:example.com` is already a real Search Console identifier.
- **Escape closes from any control inside the detail** except (a) a `<select>`, (b) the focused control that IS an open trigger (`aria-expanded="true"` with `role="combobox"` or a non-dialog `aria-haspopup`), (c) anything inside a floating popper layer or a `menu` / `menubar` / `listbox` / `tree` / `grid`, and (d) a text field with uncommitted edits (`value !== defaultValue`). `isTypingTarget` is still the rule for the ARROWS — a caret belongs to the field — but it swallowed Escape on the presentation pane's checkbox (NEW-6). 🚨 **The predicate is narrow ON PURPOSE** (NEW-11): matching any ANCESTOR with `data-state="open"` or `aria-expanded="true"` swallowed Escape under every Radix Collapsible and Accordion section a record type renders, and under a Drawer's content — which the docked and window presentations ARE on a phone — so the detail's only keyboard exit died inside an expanded section. A Dialog/Drawer role is excluded for exactly that reason.
- **A per-type save is a MERGE AT THE PERSON'S OWN RUNG that can refuse.** `ui.detail.presentation_by_type` holds every type's exception in one json map and the write door replaces the whole value, so `savePresentation` never merges into a guess: an unreadable map refuses the write and the pane shows the refusal (`data-detail-presentation-refusal`). The base is the USER rung's own map, read through `platform.knob_override`, NEVER the effective (organization → user) answer — merging the effective map and writing it at the user rung copied the organization's exceptions into the person's row, where they stopped tracking the organization for ever (NEW-3).
- **The source health strip HAS a producer.** `DetailRecordType.health` is a sync-OR-ASYNC producer the host wires (`DetailHealthProducer`, resolved by the ONE hook `useDetailHealth`, so the hook order cannot change when the person arrows from a synced record to an owned one); `resolveItemDetailType` attaches `sourceHealthProducerFor(type)` (`features/item-presentation/sourceHealth.ts`), which recognises a synced row by the columns it carries (`provider` + an external id), maps it to a connector product, and derives the strip from the connectors' own `productHealth` over the server's recorded `capability_health` — never a second reader of that column. A producer that throws renders an honest "we could not check the connection" strip, never silence. The Reconnect is the host's `reconnectSource` port (the Google connect window, i.e. the same incremental consent the connector rows run) and is offered only when a fresh grant is really the repair — a quota or an outage says so instead (PLAN §5.3).
- **`check:settings-unregistered` names neither `ui.detail.presentation_by_type` nor `ui.detail.default_presentation`** — both knob rows are registered and live (`migrations/detail_presentation_knob.sql`, `migrations/detail_presentation_by_type_knob.sql`, both ledgered 2026-09-17). It does not name `ui.detail.list_context_max_ids` either — that row is live and ledgered too (2026-09-17 20:04Z). `migrations/detail_list_context_max_ceiling.sql` is applied (20:48:24Z) and the pending `migrations/detail_list_context_max_deliverable.sql` only edits that row's `max_value`, starting value and basis text, so the guard stays quiet whether or not it has been applied.
