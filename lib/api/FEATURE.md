# FEATURE: Python API client — contract-bound calls

**Status:** Active · **Owner:** platform · **Entry point:** [`lib/api/typed-client.ts`](./typed-client.ts)

The single sanctioned way for feature code to call the Python backend
(`https://server.app.matrxserver.com`). It binds every callsite to the
server's OpenAPI contract so a wrong shape is a **compile error**, not a
runtime 400.

> This exists because a wrong shape shipped to production. The FE hand-wrote
> `PreviewVariantSpec` with a `key` field; the backend had renamed it to
> `preset_id`. TypeScript was green because it checked a hand-written copy
> against itself — nothing linked it to the real contract. Users hit
> `invalid_variant_spec: preset_id Field required` (Image Studio → Convert).

## The two rules

**1. Types are DERIVED from the generated contract, never hand-mirrored.**
The source of truth is `types/python-generated/api-types.ts` (regenerated by
`pnpm sync-types`). Request/response types alias the generated schema:

```ts
// ✅ derive — drifts loudly when the backend changes
export type PreviewVariantSpec = components["schemas"]["PreviewVariantSpec"];

// ❌ hand-mirror — drifts SILENTLY; this is the bug class
export interface PreviewVariantSpec { key: string; /* … */ }
```

The rest of `features/files/types.ts` already models this
(`FileRecordApi = components["schemas"]["FileRecord"]`, …). `assets.ts` was
the deviation that shipped the 400.

**2. Every backend call goes through the typed client, never the raw helpers.**
`lib/python-client.ts` (`postJson<T>`, `postMultipart<T>`, …) takes a plain
`string` path and an *asserted* response `T` — no link to the contract. Feature
code uses `lib/api/typed-client.ts` instead, which is generic over a **path
literal** and derives body + response from `operations[…]`:

```ts
import { apiPost, apiGet, apiMultipart, buildPath } from "@/lib/api/typed-client";

const { data } = await apiPost("/assets/preview", body); // body + data typed from contract
const { data } = await apiGet(buildPath("/assets/{file_id}", { file_id }));
```

What this catches at compile time: wrong path (not a key of `paths`), wrong
body shape/key, wrong response field. When `pnpm sync-types` regenerates the
contract after a backend change, every drifted callsite lights up red in the
same PR.

## Multipart nuance (read before touching a `*/multipart` call)

FastAPI multipart bodies encode JSON fields as **strings** at the wire
(`variants_json: string`), so OpenAPI can't carry the *inner* type. `apiMultipart`
still derives the **response** from the contract (killing the `<T>` assertion),
but the caller builds the `FormData`. Keep the inner payload safe by typing the
object you `JSON.stringify` against its generated `components["schemas"][…]` type
— then a rename breaks the `.map()` that builds it. Prefer the JSON sibling
endpoint (`/assets/preview`) when raw file bytes aren't required; it's fully
typed end-to-end.

## Proof / guardrail

[`typed-client.contract-test.ts`](./typed-client.contract-test.ts) is a
type-checked (never executed) file of `@ts-expect-error` assertions. If
`pnpm type-check` reports an *unused* `@ts-expect-error` there, the guarantee
regressed — the client stopped catching a wrong shape. Do not delete assertions
to make it pass.
