## The model

**1 atom** — the **Shape**: a named, versioned structure. Home: `content_ir.kind_definition` + `kind_edge`, read via `kind_definition_version`.

**Target: 7 assets per independently usable Shape:** schema · skill(s) · content block · output component · input component · samples (`kind_example`) · Pydantic mirror. Nested-only and data-only kinds have explicit structural exemptions; current coverage is generated in `SHAPES_STATUS.md` and summarized cross-repo in the system-of-record.

**Target: 3 machines:** detection (`kind_surface` should drive every Shape surface and normalize it to canonical `__kind` JSON at the boundary) · registry/resolver (`kind_component`: (kind, platform, role) → component) · artifact + state. Detector bootstraps generate from `kind_surface` for both runtimes (see "Coverage gates"); host-literal deletion is gated on the Wave-2 ratchet, and full artifact adoption remains incomplete.

**Target: 4 consumer families:** agent outputs · workflow node I/O · tool inputs/results · custom apps. Workflow kind primitives are live; adoption across nodes/actions and the other families is incomplete.

**THE KEYSTONE — convergence at detection.** A Shape arrives on many surfaces (`__kind` JSON, XML tags, fences, tool results, markdown). The instant a detector recognizes Shape X it emits the canonical `__kind` JSON; the arrival format is discarded. Below the boundary everything is format-agnostic **by construction**. Split-per-format assets (skill, content block, detection) sit ABOVE the boundary; shared assets (schema, components, samples, pydantic, artifact/state) sit BELOW.

## The posture (read before judging any inventory)

- **Importance inversion.** What adheres today (flashcards, quiz) was the low-stakes testbed. What doesn't adhere (Matrx Actions, the XML render pipeline, the variable form system, tool results) is the mission-critical production material that was deliberately kept off the system until it had a real home. **Adoption = bridging real systems IN, not polishing testbeds.**
- **Borrow, don't conquer.** The render pipeline (`content-splitter-v2` + accumulator) transitions to **dual-mode**: XML stays a first-class *input surface* permanently (LLMs emit it easily); `__kind` JSON is the *internal* form. Content blocks are a borrowed delivery vehicle into the user's context menu — we don't own that system. The form system (`VariableDefinition` → `VariableInputComponent`) is production — the input-component asset is a **bridge** to it, never a new form builder.
- **Matrx Actions is the elder sibling** — the origin system this generalizes, live in production. Its 12 invariants are constraints on us (envelope detected by `matrx_version` presence only; position invariants; handler = only side-effect path; no parallel encodings; …). The only sanctioned touches near it: the kind-slug collision guard and a ` ```matrx ` `kind_surface` row routing to the protocol handler. Actions↔kinds convergence is deferred (Arman's call); `kind_definition.metadata` carries the safety vocabulary (`category: pure|side_effect|sensitive`) so either direction needs no schema change.

## The Convert Pattern (ratified 2026-07-15) — some content does NOT start as a `__kind`

**Markdown-first content renders through a rich generic component; promotion to a kind/artifact/live entity is an explicit USER action (a button) — never automatic.** Adoption leans maximally non-breaking, and this is the one deliberate ceiling: when the plain form IS the content contract, detection would destroy value, not add it. You click to convert.

- **`table` is the exemplar — permanently `scalar_generic`, never auto-kind.** The markdown table is the core content (it stays in `cx_message.content`, so the model's history matches what the user sees); `StreamingTableRenderer` renders it richly (edit, sort, export, save). **Convert to table** (`features/canvas/artifact-types/renderers/TableArtifact.tsx`) links a real `udt_datasets` row via `createDatasetFromTable`, after which the live realtime `UserTableViewer` renders from the dataset — and **Revert** unlinks it (dataset kept, markdown untouched). The ruling is encoded in the crosswalk `table` rationale (`generate-content-vocab-crosswalk.ts`) and aidream `envelope.py` `NON_ENVELOPE_BLOCK_TYPES["table"]` — do not "fix" either by registering a table kind.
- **The shipped convert machinery is `features/canvas/materialization/`** — notes fence/kind-JSON → artifact (`useNoteArtifactMaterialization` → `materializeBlocks({system:"note"})`, the "Convert blocks to artifacts" editor action) and chat attach/detach (`attachBlockAsEditableContext` / `unbindArtifact` / `flipMessageToDbRender`). Build new convert affordances on it; never a parallel path.
- **Decision rule for a future kind — convert-pattern vs auto-kind.** Choose **convert** when the plain/markdown form is the durable contract (round-trips the DB, feeds model history), rich rendering already works without identity, and promotion creates a NEW stateful entity (dataset, artifact, task). Choose **auto-kind** (`kind_surface` detection) when the payload is born structured and the win is validation + shared rendering with no ownership change. Every convert MUST have a way back (Revert; the original text is never destroyed).
- **Registration without detection is legal and useful.** The 2026-07-17 candidate registration (chart, map, stats, diff, search_results, fetch_results, categorization_result) gives splitter/data-event blocks identity, validation, and coverage with ZERO surface rows — arrival and rendering unchanged. Identity and detection are separate decisions.
- **`schema_proposal` has TWO apply targets (2026-07-17).** Beside "Apply to an agent" (writes `agent.definition.output_schema`), **"Create a Shape"** registers the proposed JSON Schema as a kind: `SchemaProposalBlock` → `CreateShapeDialog` → `features/agents/components/schema-proposal/create-shape.ts`, which runs the CANONICAL pipeline (`runSchemaConversion` → `planKindMigration`) and inserts ts-owned `kind_definition` rows (root + nested child kinds, `is_active=false`, `metadata.source='schema_proposal'`) + `kind_edge`s + one canonical `kind_example` — all via the browser supabase client (RLS is the authz; creator = owner). The sample is REQUIRED, ajv-pre-validated with `validateStructuralLeg`, and the DB trigger's verdict is read back — a non-`passed` verdict surfaces loudly with fix-and-retry, never a silent broken kind. Success deep-links to `shapeDetailHref(slug)` (/shapes/[kind]).
- **Chat is a shipped convert surface (2026-07-17).** Assistant messages carrying a markdown table or list get a "Convert to flashcards / quiz…" action (`messageActionRegistry.ts` → the canonical `ConvertContentDialog`, `features/education/convert/`) — content stays generic markdown until the explicit click, and the created artifact lineage-links back to the conversation.

## DB kind components (`source='db'`, live 2026-07-17)

**R1's db source is REAL: a `kind_component` row can carry the component itself.** Ratified architecture (Arman, 2026-07-17): user components run via the **in-page allowlist compile** — the shared Agent Apps compiler (`compileSlotComponent` over `buildComponentScope`, allowlist deliberately WIDE per the ratification) — with an **iframe/html flavor as a user OPTION** (not a trust tier). Renderer: `features/content-ir/react/db-component/` (lazy shell → Impl, Babel never in the main bundle — the DbToolRenderer pattern).

**The db-row contract** (`content_ir.kind_component`):
- `source='db'` + `is_active=true` + non-empty `component_source` → `applyIrKindRoute` flips the block to `db_kind_component` — **db overrides bundled AND the compiled bridge** (R6); inactive rows do not route; an active db row with NO body **screams and falls through** to bundled behavior (never un-renders).
- `component_source` — react flavor (default): TSX/JSX; must `export default` a component receiving **`{ data, kind, config }`** (`data` = the kind instance value). html flavor (`config.flavor='html'`): a full HTML document rendered via srcDoc `sandbox="allow-scripts allow-forms"` — **NEVER `allow-same-origin`**; kind data arrives via BOTH the appended `<script type="application/json" id="matrx-kind-data">` slot (`{kind, data}`, read after load) and a `{type:'matrx:kind-data', kind, data}` postMessage on load (`KindHtmlFrame.tsx`).
- `props_transform` (optional) — `(data) => data` source compiled the same way, applied BEFORE the component (tool_ui transform semantics). Throwing/broken transform screams; untransformed value renders.
- `config.allowed_imports` (string[]) narrows the scope; absent → the FULL registered allowlist (`getDefaultImportsForKindComponents` in `features/agent-apps/utils/allowed-imports.ts` — the ONE shared allowlist; every entry explicitly named, unknown identifiers keep the safe-proxy fallback).
- `pinned_kind_version` rides the projection (reserved for version-pinned rendering).
- **Row selection is deterministic:** `is_default DESC, sort_order ASC, created_at ASC, id ASC` (`sortKindComponentRows`, applied in SQL and client-side; first row per (kind, platform, role) wins). **`is_default` is a PREFERENCE among db rows, not a trust gate** — the trust gates are `is_active` (render trust, R6) and RLS editor access on the row itself.
- Failure posture: compile error / render-or-lifecycle throw / unresolvable row → the kind's **generic structured viewer + loud report** (`captureError` source `content-ir`, one console scream per key) — never a blank hole, never hidden content. (React error boundaries catch render/lifecycle throws only; errors in async code, effects, and event handlers surface through the standard error capture, not the boundary.)

**Staleness contract — refresh-on-view, no push.** A server-side edit to a db row does NOT reach already-open clients (no realtime yet). The compile cache keys on the row's `updated_at` (one compile per row VERSION), and `refreshKindComponents()` / `subscribeKindComponents()` (`component-registry.ts`) re-fetch the warm list, replace the db tier, and notify — rate-limited + deduped, safe on every preview mount. `KindInstanceRender` (studio/admin previews) already calls it on mount; any authoring surface that edits a row calls it (or `invalidateDbKindComponent`) after save. Chat sessions pick up edits on the next warm load (new session).

First live rows: `stats_db_demo` (react + transform) and `diff_db_demo` (html) via `migrations/content_ir_db_source_demo_components.sql` — proof surfaces `/administration/utilities/kind-registry/stats|diff` Preview.

## Streaming db/cloud kinds + the loading library (live 2026-07-18)

**Any `__kind` known only to the DB renders LIVE during streaming, everywhere the accumulator runs.** The mechanism (all shipped, browser-verified on `wine_tasting`):

- **Kind preservation (kernel):** the envelope NEVER blanks an identified kind. While the schema cold-fetches, `root.kind` carries the identified slug with `kindState: "pending_schema"`; if the region ends before the answer, the raw fallback PRESERVES the kind (`raw_object.kind`, schema-availability failures only — structural raws stay kind-less). Routing boundary: a kind-preserved raw routes to the **generic structured viewer, never raw JSON, ONLY when the kind's definition IS registered** (the schema-race/db-kind case); an UNREGISTERED `__kind` (typo, teaching content showing a hypothetical payload) stays a readable raw code block exactly as before — registration separates "known but unrenderable" from "not ours to claim". Genuinely kind-less JSON keeps legacy behavior byte-identically (test-pinned: `streaming-db-kind-preservation.test.ts`, `kind-route.test.ts`).
- **Eager lightweight fetch:** the instant the parser identifies a cloud kind (`kind_identified`/`pending_schema`, surfaced through the session `onEvent` seam), the accumulator fires the schema cold-fetch AND `componentRegistry.requestComponent(kind,"web","output")` → `getKindComponentBySlug` (render-essential columns ONLY; in-flight deduped per (kind, platform); misses cached per (kind, platform, role) and CLEARED on every wholesale refresh, so a component created mid-session becomes eagerly fetchable again). **(web, output) is deliberate** — chat streaming renders exactly that surface; other roles/platforms ride the warm/refresh path by design. Both registries also `ensureWarm()` at region open — the streaming path warms the COMPONENT registry too (its absence was the "shows as JSON" bug).
- **Late-arrival repaint (GRANULAR):** both registries carry PER-KIND version counters (+ a wholesale epoch for `replaceDbRows`); `useContentIrKindVersion(kind)` (`react/use-registry-repaint.ts`, `useSyncExternalStore`) subscribes each block to ITS envelope kind only, and BlockRenderer memoizes the route on (block, kindVersion) — an arrival for kind X re-renders only mounted kind-X blocks, never every block in every conversation (React Compiler is OFF in this repo, so the explicit memo is load-bearing; acceptance test: `kind-repaint-granularity.test.tsx`). Dispose stays — repaint works from the persisted envelope + registries, no session held open.

**The loading library** (`features/content-ir/react/loading/`) — 20 hardcoded, zero-fetch loaders: `card list table timeline chart deck form media stat-grid document diagram chat gallery kanban tree code map progress minimal generic`. Selection: **`kind_definition.metadata.loading_component`** names a slug (read via the warm entries + cold fetch; the studio/creator agent sets it); missing/unknown → `generic`. Growing it = component in `kind-loading-components.tsx` + row in `kind-loading-registry.ts` + slug documented here.

**The early-key contract** (teach emitters to order these keys FIRST in schema + samples): while a kind instance streams pre-schema, the parser emits un-validated top-level scalar `field` events and the tree accumulates them on the envelope's root value. The loading layer reads this default set: `title`, `description`, `loading_message`, `loading_subtext`, `icon` (an `ICON_HINTS` slug), `count` (drives skeleton row count). All optional; every loader renders bare. Once the schema lands, compliant snapshots supersede early values (unknown-to-schema keys become residue as usual).

**The observed live sequence** (wine_tasting, browser-proven): fenced `__kind` json opens → generic loader with live early keys (title + loading_message + subtext) → definition warms → the kind's declared `card` loader (repaint) → schema resolved → route flips to the `db_kind_component` (the user's actual card, partial data streaming in) → complete. A plain `json` fence with no `__kind` stays a code block throughout.

## Owner authoring on `/shapes/[kind]` (live 2026-07-21)

- **Ownership, not mere visibility, unlocks editing.** `shape-detail-server.ts` compares the viewer to `kind_definition.created_by`; granted/internal/public library rows stay read-only. This client hint is not authorization: every mutation in `studio/shape-authoring-service.ts` re-reads the definition under the current user, scopes the write to that owner, and still relies on canonical RLS.
- **Preview is the CRUD home.** `ShapeOwnerEditor` manages authored `kind_example` rows (create, update, promote canonical, soft-delete non-canonical) and the safe definition settings: label, visibility, `metadata.title_key`, and `metadata.loading_component`. Sample JSON uses the canonical lazy `JsonInspector`, runs `validateStructuralLeg` before save, then reads the DB validation trigger's verdict back; disagreement is loud validator drift.
- **Definition version bumps are never allowed to strand samples.** The platform touch trigger increments `kind_definition.version` even for label/metadata edits. A successful profile save immediately updates every live example to the new `kind_version` and requires every recomputed trigger verdict to remain `passed`; partial failure tells the user the definition saved but examples need repair.
- **Canonical continuity is enforced.** The first example becomes canonical. Canonical rows cannot be deleted until another example is promoted; promotion clears the old flag, promotes the new row, and attempts to restore the previous canonical row if the second write fails.

## Activation — the ONE write path for `is_active` (live 2026-07-22)

Until this shipped **nothing could write `is_active`**: the agent toolset hardcoded `false`, the studio had no write, and the admin console declares read-only as an invariant. Activation was a human hand-writing a migration per kind, so six agent-authored kinds sat permanently dark holding a validated canonical example AND a live `source='db'` component — both legs satisfied in substance, no way to record it.

- **`content_ir.set_kind_activation(id, active, note)` is the only write.** It runs the gate server-side and RAISES with the gate's own reasons (naming the missing asset) rather than refusing silently. Owner-or-super-admin. **Deactivation is never gated** — a kind whose component starts failing must always be switchable off. `content_ir.evaluate_kind_activation(id)` is its read-only twin ("why won't this activate?"), safe to call on render.
- **Both legs reuse verdicts that already exist; there is no third validator.** Structural = a canonical `kind_example` whose `validation_status='passed'`, a value DERIVED by the `kind_example_recompute_validation` trigger, so a fabricated pass is impossible. Render = an active `role='output'` `kind_component` row, which covers compiled (`source='bundled'`) and agent-authored (`source='db'`) components identically.
- **The render leg is `n/a` for data-only contract families** (`workflow_io`/`tool_io`/`action_io`/`agent_io`) — 746 active generated kinds legitimately own no component, and failing them would be noise. Same `data_only` doctrine the shape doctor uses.
- **Render-leg satisfier ORDER is load-bearing** (`kind-dual-gate.ts`). The compiled-bridge check is the strongest satisfier — it exercises the bridge and catches the "No `<kind>` available" class (the 2026-07-04 flashcards regression). Every compiled kind *also* owns a bundled `kind_component` row, so checking the resolved component first would short-circuit past the bridge for exactly the kinds that guard protects. The resolved component is the LAST resort, never the first. Pinned by `__tests__/kind-dual-gate.test.ts` § satisfier precedence.
- **Surfaces (`kind_surface`) are deliberately NOT agent-automated.** A surface row is inert without a `parser_strategy` implemented in TS (`surfaces/xml-finalize.ts#SURFACE_PARSER_STRATEGIES`), and registering one without its parser mints exactly the phantom rows that already exist for the 8 `json_root_key` surfaces. A new kind's arrival form is `__kind` JSON, which the parser detects natively and which needs no surface at all.
- **Surfaces:** owner control on `/shapes/[kind]` (`studio/components/ShapeActivationControl.tsx`, blockers listed verbatim); agent tool `kind_activate` (aidream `kind_authoring.py`), which calls the same `evaluate_kind_activation` so browser and agent can never disagree. The admin Gate tab stays READ-ONLY on purpose — it is what you check *after* a change.

## Kind instances — user persistence (live 2026-07-18)

**`content_ir.kind_instance` is where a user's saved data of any kind lives** (P-1 DB contract: pinned `kind_version`, trigger-DERIVED `validation_status`, caller's-org row, canonical RLS). Frontend rules:

- **ONE browser write/read path:** `studio/instance-service.ts` (save / list / update / repin / soft-delete) — direct supabase-js, never Python. It mirrors the aidream `instance_*` toolset EXACTLY: `data` stores pure payload (root `__kind` stripped), `title` derives via `studio/instance-title.ts` — explicit → the kind's `metadata.title_key` override (set by `kind_create`; non-empty scalar) → the shared `INSTANCE_TITLE_KEYS` list (= server `_TITLE_KEYS`; order mirrored verbatim by aidream `derive_title`) — and every write **reads the trigger verdict back** — a non-`passed` verdict after a client-side ajv pass is validator drift: `captureError` + show the user, never hide.
- **Version pins are FRESH, never page-load snapshots:** save and repin re-read the definition's live `version` (+ `emitted_json_schema` for repin) at write time; a mid-session bump surfaces as `versionBumped` → inline notice on the Test tab ("Shape updated to v{n} since you opened this page").
- **Repin is honest:** `repinKindInstance` validates the data against the CURRENT `emitted_json_schema` first and refuses loudly on failure — never a blind version bump (P-1 parity).
- **Edit round-trip preserves stored `""`:** `emptyStringSeededFields` + `assembleKindInstance`'s `emptyStringFields` option keep a string field legitimately holding `""` from being omitted on re-save (test-pinned).
- **Reserved slugs:** `RESERVED_SHAPE_SLUGS` (studio/constants.ts — the static `/shapes` segments: `instances`, `new`, `admin`) are refused at creation (`findTakenSlugs` + CreateShapeDialog "reserved" status); a kind with one of these slugs is unreachable by routing. New static segment under /shapes = add its slug.
- **Surfaces:** Test tab Save (`ShapeTestTab`) → toast + "View in Instances"; `/shapes/[kind]/instances` (`ShapeInstancesTab`, ssr:false loader) — list (validation dot, pinned-version chip when `kind_version` < current), render through `KindInstanceRender`, Edit via `KindInputForm initialValue` (the additive prefill prop; inverse seeding = `initialValuesFromInstance`, test-pinned round-trip), soft Delete (`ConfirmDialog`), Repin.
- **Permalink:** `/shapes/instances/[id]` resolves kind → redirects to `/shapes/[kind]/instances?i=<id>`; it IS the sharing-registry `url_path_template` for `content_ir_kind_instance` — keep them in lockstep (`shapeInstancePermalink`).
- **Save-from-chat:** assistant-message action "Save to my Shapes" (`messageActionRegistry` → lazy `studio/message-kind-instances.ts`); hot-path gate is `studio/message-kind-gate.ts` (marker substring + auth). Extraction reuses the materialization detection (splitter → envelope `reconstructRegionValue` → JSON-parse fallback), gated on registry resolution — never a bespoke re-parse.
- **Dataset interop = the Convert Pattern, read-only v1:** "View as table" on the Instances tab (FLAT fielded kinds only) snapshots instances into a NEW dataset via `createDatasetFromTable` — no sync, no substrate.
